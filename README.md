## Эталон и метод

**Эталонный исход или прокси:** отдельная Python-функция разбирает число и единицу каждого объекта, приводит значения одной физической размерности к общей базовой единице и проверяет неубывающий порядок. Перестановка считается правильной тогда и только тогда, когда каждое следующее нормализованное значение не меньше предыдущего. Прокси реализуется независимо от исходного кода оценщика и не использует `reward`, `done` или `getGoldActionSequence()`.

**Приращение проекта:** независимый нормализатор физических единиц и полный перебор перестановок объектов для воспроизводимого аудита штатного оценщика Sorting. Поддерживаемые единицы: масса — `mg`, `g`, `kg`; длина — `mm`, `cm`, `m`; объём — `ml`, `l`; количества без единиц сравниваются отдельно. Для нормализации используем точную арифметику, чтобы ошибки округления не создавали ложные равенства.

Перед перебором фиксируем для каждого эпизода физическую размерность и наличие равных нормализованных значений. Если обнаружены разные размерности, включая смешение величин с единицами и без них, присваиваем статус «несравнимые величины»: общий порядок не вычисляем, эпизод разбираем отдельно. Эпизоды с равными значениями выделяем в отдельную группу и выясняем правило среды по исходному коду оценщика и воспроизводимым примерам. До выяснения правила все перестановки таких эпизодов исключаем из основных `FP`, `FN`, `TP` и знаменателя `N`; их число и результаты показываем отдельно. Те же правила исключения действуют для несравнимых величин. В каждом запуске явно указываем числа таких эпизодов, даже если они равны нулю, и не заменяем исключённые seed.

Прокси проверяет только математическую правильность порядка. Он не покрывает качество естественно-языковых формулировок, допустимые синонимы команд, удобство интерфейса, эффективность агента и физические единицы, которых нет в генераторе.

**Ручная сверка прокси:** участник команды независимо от результатов прокси и сигналов среды разбирает исходные величины, записывает размерность, приведение единиц и правильный порядок, затем сопоставляет их с прокси. Проверяем первые по возрастанию seed пять разных эпизодов из каждого непустого пересечения «число объектов × вид единиц»; если в группе меньше пяти эпизодов, проверяем все. На текущем наборе это **33 разных эпизода**. Таблица [ручной сверки](docs/manual_proxy_review.csv) содержит исходные объекты и выбранные seed; поля ответа человека, проверяющего, даты и результата пока не заполнены, статус всех записей — `pending`. Ручная сверка ещё не выполнена. После её выполнения сохраняем также ответ прокси и все расхождения; ошибки нормализатора исправляем и пересчитываем затронутые результаты. Окончательный вывод о согласованности делаем после завершения ручной сверки и устранения ошибок прокси.

**Протокол исполнения перестановки:**

1. Перед каждой перестановкой сбрасываем среду с теми же `seed`, `gameFold="test"` и настройками, включая `generateGoldPath=False`.
2. Для каждого объекта в заданном порядке выполняем `take <объект>`, затем `put <объект> in box`; перед действием проверяем его наличие в текущем списке `validActions`.
3. После каждого действия записываем результат и немедленно останавливаем исполнение при первом `done=True`, в том числе между `take` и `put`. После этого не вызываем `step` до сброса среды для следующей перестановки. Среда позволяет продолжать действия после `done=True` и затем получить `score == 1.0`, поэтому продолжение исказило бы оценку.
4. Математическую правильность проверяем для задуманной полной перестановки, даже если среда отклонила её до исполнения всех действий.

**Оцениваемый оценщик:** штатное решение среды TextWorldExpress о принятии или отклонении порядка. При штатном завершении порядок считается принятым, если на первом `done=True` получен `score == 1.0`; в остальных случаях штатного завершения он считается отклонённым. Сигналы `reward` и `done` сохраняем в протоколе для разбора, но корректность каждой промежуточной награды и момента завершения отдельно не оцениваем.

Ошибки парсинга, недопустимые команды, сбои среды и исчерпание лимита без штатного успеха или неудачи задачи фиксируем отдельно как ошибки прокси или протокола, а не как `FP`/`FN`. Устраняем их и повторяем затронутые прогоны; до этого итоговый критерий не считается проверенным. Такие случаи нельзя молча исключать из выбранного набора или заменять другими seed.

**Базовое сравнение:** простой `numeric-only`-оценщик, который сортирует только по записанному числу и игнорирует единицы и их масштаб. Сравнение покажет, даёт ли приведение единиц преимущество именно на эпизодах со смешанными приставками.

## Метрика и критерий

**Метрика ошибки:** доля расхождений

```text
disagreement_rate = (FP + FN) / N
```

где `FP` — число перестановок, которые среда приняла (`score == 1.0` на первом `done=True`), а прокси признал неправильными; `FN` — число перестановок, которые среда отклонила, а прокси признал правильными; `TP` — число математически правильных перестановок, принятых средой; `N` — общее число перестановок, исполненных по протоколу в основном наборе сравнимых эпизодов без равных значений, включая отклонённые до конца последовательности действий. В отчёте выражение вычисляется как `(FP + FN) / N`; отдельно приводятся `FP / N`, `FN / N`, доля ложных отклонений среди правильных порядков `FN / (TP + FN)`, абсолютные количества, числа исключённых эпизодов и результаты по каждому срезу.

При `N=0` указываем `N/A` для долей с этим знаменателем, сохраняя `N=0` и абсолютные количества. При `TP + FN == 0` указываем `N/A` для доли ложных отклонений. Отсутствие данных не трактуем как нулевую ошибку или подтверждение качества на этом срезе.

**Численный критерий успеха:** отсутствие наблюдаемых расхождений на выбранном каталоге: **`FP = 0` и `FN = 0`** в основном наборе после обработки всех запланированных перестановок, устранения ошибок прокси и протокола и завершения ручной сверки. Отдельно приводим результаты исключённых групп и пустые срезы. Ненулевые расхождения сохраняем как контрпримеры для разбора оценщика и прокси.

Долю `FN / (TP + FN)` сопровождаем **двусторонним 95% интервалом Уилсона** в целом и по каждому срезу. Метод и формула приведены в [справочнике NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm). При `x = FN`, `n = TP + FN`, `p = x / n`, `z = 1.959963984540054` границы вычисляются как:

```text
center = (p + z² / (2n)) / (1 + z² / n)
half_width = z * sqrt(p * (1 - p) / n + z² / (4n²)) / (1 + z² / n)
Wilson95 = [max(0, center - half_width), min(1, center + half_width)]
```

Для нуля ошибок интервал равен `[0, z² / (n + z²)]`: при `n=100` верхняя граница — **3,70%**, а не 1%. Около 3% по «правилу трёх» — приближение односторонней верхней границы; это другой расчёт. Даже при 300 независимых задачах двусторонний интервал Уилсона при нуле ошибок имеет верхнюю границу около 1,26%. На малых срезах неопределённость ещё выше, поэтому статистическое подтверждение частоты ошибок ниже 1% не заявляем.

Перестановки одного эпизода зависимы: 5544 перестановки не считаем 5544 независимыми испытаниями. Общая доля `(FP + FN) / N` описывает полный перебор выбранного каталога. Для оценки на уровне эпизодов дополнительно приводим число разных задач `E` и долю задач хотя бы с одним расхождением `E_error / E` с интервалом Уилсона. При различных значениях на задачу приходится один правильный порядок, поэтому `TP + FN = E`; в текущем нулевом прогоне интервалы для обеих долей совпадают. Интервалы служат модельным ориентиром при предположении независимости задач. Каталог фиксирован, а его полный перебор не является случайной выборкой новых задач: эти интервалы не доказывают перенос результата за пределы каталога.

## Риск и границы

**Возможная ошибка оценщика:** среда может выдать `score == 1.0` для неверного порядка из-за неправильного преобразования приставок (`mg`, `g`, `kg` и аналогичных единиц), сравнения строк вместо нормализованных чисел, ошибки округления или неверного правила для равных значений. Возможна и обратная ошибка: правильный порядок будет отклонён.

**За границами проекта:** обучение и сравнение RL-агентов; остальные семь сред TextWorldExpress; train/dev-срезы; проверка корректности всех промежуточных наград и момента завершения; производительность симулятора; полный обход карты или дерева состояний; оценка языкового разнообразия; добавление новых объектов и единиц; доказательство корректности всей библиотеки.

4. **Следующий шаг можно сделать за 2–3 дня, и у него есть ответственный?** Да: плановая длительность — 2–3 дня; ответственный — Воробьев Д. В. Новая календарная дата требует согласования, а ручная сверка пока ожидает выполнения.
